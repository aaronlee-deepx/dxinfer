dxinfer architecture

dxinfer loads several .dxnn networks onto a DEEPX NPU at once. It keeps every network's device slots full and gives each network's results back in feed order. The output tensors are never copied. This page is a map for reading the code: what each part is, who owns what, and the path one input takes from feed() to your result.

1. Layers and modules

There are four layers. Your code only ever talks to the two public classes. Each loaded network is one internal detail::Network. The building blocks under it don't depend on dx-runtime, so they're unit-tested on any host. Only detail::Network touches dx-runtime.

2. Who owns what

Lifetimes explain most of the design. The one surprising edge is at the bottom. A Result holds a pool block, and the block holds a shared_ptr to its pool. So a result you keep stays valid even after the inference object is destroyed.

3. The pipeline: one input, three threads

Each lane is a thread. Async mode is shown. In sync mode the middle lane doesn't exist: Run() returns on the feeder thread, and complete() runs right there. Two dashed feedback edges keep the device full. Freeing a slot wakes a waiting feeder, and dropping a Result returns its block to the pool.

4. Walkthroughs

a. Construction: loading every network, all or nothing

  1. Check the arguments before touching the device. An empty list or extra_result_buffers < -1 gives InvalidArgument. Names are checked next: an empty name, or a duplicate (DuplicateName).InferenceBase::InferenceBase · src/inference_base.cpp
  2. Create the networks in order. If any one throws, nets_.clear() releases the engines already loaded, which frees their NPU memory. The error is rethrown with "already loaded and now released: …".InferenceBase::InferenceBase
  3. Inside each network, first check bound (0..6) and buffer_count (0..100).detail::Network::Network · src/network.cpp
  4. Read the task graph and decide ORT before dx-runtime sees the file. resolve_ort prints the scenario-1 hint or the reader WARNING. It throws InvalidArgument for ort=off on a model with two or more NPU tasks.read_model_graph → resolve_ort · src/model_graph.cpp
  5. Create the engine with bufferCount, boundOption, devices, useORT and showModelInfo=false. A dx-runtime exception goes through load_error. An NPU memory failure becomes OutOfDeviceMemory, and the message includes each device's free MiB. Anything else becomes LoadFailed.Network::Network · load_error · free_memory_report
  6. Fill NetworkInfo. This covers the model name, version and compile type, PPU, effective ORT, and the input and output tensors with their offsets in the block. For multi-input models it also records input_parts_. Then buffer_count (0 means $DXRT_TASK_MAX_LOAD, or 6), max_in_flight = buffer_count × device_count, and result_buffers = max_in_flight + extra.Network::build_info
  7. Check what dx-runtime really loaded. loaded_tasks = GetTaskOrder().size() is compared with the graph. If the model needs ORT but dx-runtime dropped it, the result is LoadFailed. Otherwise you get a warning.check_loaded · src/model_graph.cpp
  8. Allocate everything once. The result pool, the low-buffer watch (only when there are at least 2 spare blocks), the max_in_flight job slots and, in async mode, RegisterCallback. The callback only calls complete().Network::Network
  9. CallbackInference only: start one Lane thread per network.CallbackInference::CallbackInference · src/callback_inference.cpp

b. Feeding one input

  1. feed and try_feed look up the network (UnknownNetwork if the name doesn't exist) and call the virtual check_can_feed. CallbackInference uses that hook to throw NoCallback until set_callback has been called.InferenceBase::feed / try_feed
  2. A null input gives InvalidArgument, and a byte count other than input_size gives BadInputSize.Network::submit
  3. Take a job slot. feed waits on slot_cv_, and try_feed returns false instead. If the network is closing, it throws ShuttingDown.Network::acquire_job
  4. Take a result block from the pool. This waits only when your application is holding every block.BufferPool::acquire / try_acquire
  5. Assign seq (an atomic counter), store user_arg, count fed_, and call stats_.on_feed.Network::submit
  6. Hand the job to dx-runtime with the block as the output buffer.
    • Async: RunAsync(in, job, block). job must not be touched after this call, because it may already be complete.
    • Sync: Run or RunMultiInput returns the outputs, and complete() runs on this thread.
    • Multi-input: split_input turns your one back-to-back buffer into one pointer per tensor.
    Network::submit · split_input
  7. If dx-runtime throws, complete(job, nullptr, InferenceFailed) still runs. That sequence number still gets a Result, so FIFO delivery never stalls.Network::submit

c. Completion: from device outputs to a queued Result

  1. Build tensor views over the block.
    • Outputs that dx-runtime wrote inside the block are used in place, with zero copies.
    • Anything dx-runtime left in its own memory, which is valid only during the callback, is copied into the block behind the rest.
    • If it doesn't fit, the result carries InferenceFailed.
    • When no runtime metadata is available, the static offsets in NetworkInfo are used.
    Network::make_views
  2. Record the stats, then build the Result. The block moves from the job into the result.stats_.on_complete · detail::ResultAccess::make
  3. Free the slot first. release_job notifies slot_cv_, so a waiting feeder submits the next job right away.Network::release_job
  4. Push the result into the reorder buffer under its seq, and count completed_. That count is what wait_completed waits for.ReorderBuffer::push · Network::complete
In async mode this runs on a dx-runtime thread, so complete() is kept short: it builds the views, frees the slot and pushes. Your code never runs on that thread. Callbacks run on the Lane thread instead.

d. Out-of-order completion, FIFO delivery

With several jobs in flight across NPU cores, jobs finish in any order. ReorderBuffer is a std::map keyed by seq, plus a next counter. Only the item at next can be popped. Example: jobs 0–3 are fed, and they finish in the order 2, 0, 3, 1.

EventWaiting in the mapnextReleased to you
job 2 completes{2}0nothing: 0 is missing
job 0 completes{0, 2}0 → 10
job 3 completes{2, 3}1nothing: 1 is missing
job 1 completes{1, 2, 3}1 → 41, 2, 3 back to back

A finished job that's waiting in the map has already freed its slot, so the device keeps working. It still holds its result block until it's delivered and dropped. The reorder wait statistic measures exactly this time spent waiting.include/dxinfer/reorder_buffer.hpp · push / pop / take_locked

e. Delivery: pulling vs callbacks

BlockingInference

get (blocks), try_get (never blocks) and get_for (timeout) all call results().pop / try_pop / pop_for. After a pop, hand_over calls on_delivered and on_consumed at once. The result's block stays in use until you drop the Result.

A closed queue makes get throw ShuttingDown.

src/blocking_inference.cpp
CallbackInference

Each network has a Lane thread that loops through run():

  1. pop
  2. on_delivered
  3. copy the callback pointer under the lane mutex
  4. call your callback; exceptions are caught, printed and counted in callback_errors
  5. r = Result() gives the block back
  6. on_consumed

wait_idle waits until consumed equals fed, for every network.

src/callback_inference.cpp

f. Result memory: blocks, copy_out and the warning

  • Pool size: max_in_flight + extra_result_buffers, where -1 means the same as max_in_flight. Blocks are allocated once, in the constructor. Each block is output_size bytes, rounded up to 64.
  • Who holds a block: a job in flight, a result waiting in the reorder buffer, or a Result you're holding. A PooledBuffer gives its block back when it's destroyed (reset), on whatever thread drops it.
  • Holding too many: beyond the extra blocks, the device gets fewer jobs, feed waits and try_feed returns false. Result::copy_out() makes a heap copy (uses_pool() == false) so the block goes back immediately.
  • Warning: PoolWarner prints when the free block count drops to 1, and a recovery line when it climbs back to 3. It prints at most once per second per network. It's installed only when the pool has at least 2 spare blocks, and is removed before shutdown.
buffer_pool.hpp · result.hpp · pool_warning.cpp · Network::Network

g. ONNX Runtime and the task graph

dx-runtime with useORT=false loads only the first NPU task of a model. So the ORT setting is decided from the model's own task graph, which is read from the .dxnn before loading. This is step 4 of the load walkthrough.

  • read_model_graph reads only the header and the graph JSON, never the weights. It returns NpuOnly, SingleNpuWithCpu, MultiNpu or Unknown with a reason. This is the only code that knows the file format: v7–v9 are supported, and v6 or v10+ return Unknown.
  • resolve_ort applies OrtMode:
    • Auto turns ORT on when CPU tasks exist and prints a hint that Off is faster.
    • Off on a model with two or more NPU tasks is rejected.
    • An unreadable graph gives a WARNING plus a safe default.
  • check_loaded runs after loading. It compares the graph with GetTaskOrder() and IsOrtConfigured().
  • Where it shows up: print_info shows task graph and ONNX Runtime: requested … → ….
model_graph.hpp/.cpp · tests/test_model_graph.cpp · README "ONNX Runtime (CPU tasks)"

i. Shutdown order

  1. The destructor calls close_all(). In CallbackInference this happens through stop_lanes(); BlockingInference reaches it from ~InferenceBase.InferenceBase::close_all
  2. For each network, close() runs these steps in order:
    • remove the low-buffer watch
    • set closing_ and wake feeders that are waiting for a slot; they throw ShuttingDown
    • shut down the pool, which also wakes feeders waiting for a block
    • wait until every job slot is free again, meaning all in-flight jobs have finished
    • close the reorder buffer
    Network::close
  3. Lane threads deliver whatever is still queued. Then pop returns false, and the threads exit and are joined.CallbackInference::stop_lanes · run
  4. ~Network unregisters the async callback, and the engine is released. Any Result you still hold stays valid, because its block keeps the pool alive.Network::~Network

No lock is held while calling into dx-runtime, while calling your callback, or while the pool's level observer runs. The observer is invoked after the pool lock is released.

6. Suggested reading order

  1. include/dxinfer/types.hpp: the vocabulary (spec, options, config, info, graph types).
  2. include/dxinfer/error.hpp: ErrorCode, Status, InferenceError.
  3. include/dxinfer/inference_base.hpp, then src/inference_base.cpp: the public surface and all-or-nothing loading.
  4. src/network.hpp: the members of one network. This is the heart of the library.
  5. src/network.cpp, in this order: the constructor, submit, complete, make_views, close.
  6. include/dxinfer/reorder_buffer.hpp: how FIFO order is restored, in about 100 lines.
  7. include/dxinfer/buffer_pool.hpp and result.hpp: block lifetime and copy_out.
  8. src/blocking_inference.cpp and src/callback_inference.cpp: the two delivery styles.
  9. include/dxinfer/model_graph.hpp, then src/model_graph.cpp: the ORT decision.
  10. stats.hpp/.cpp and pool_warning.*: measurement and the warning.
  11. tests/*.cpp: each building block exercised on the host, so you can read and run them as examples.
  12. examples/demo_common.hpp and the two demos: end-to-end use with FIFO and user_arg checks.
