dxinfer feature workflows

dxinfer runs several .dxnn networks on a DEEPX NPU from one object, and returns each network's results in the order they were fed. This page covers its three main features. For each one it gives the problem, how dxinfer handles it, the evidence so far, and the limits. Code-level detail is in architecture.html (online copy).

Feature 1

Auto ORT from the model's task graph

Problem: with ORT off, dx-runtime runs only the model's first NPU task, and nothing reports it. Models with CPU tasks, or with more than one NPU task, are silently cut short.

Multiple networks in one object

Problem: an application with several models has to manage several engines, their buffers, and partial-load failures.

1. Auto ORT from the model's task graph

The problem

A compiled model can be split into tasks that run on the NPU or on the CPU. The CPU tasks run on ONNX Runtime (ORT), for example a final reshape, concat or TopK. dx-runtime's useORT flag decides what happens:

  • ORT on: every task is loaded and run in order.
  • ORT off: only the first NPU task is loaded. CPU tasks are skipped, and any later NPU tasks are never loaded. No error is raised. The outputs are simply that first task's raw tensors.

For a model shaped npu → cpu that may be what you want, because you then do the CPU step yourself. For npu → cpu → npu or npu → npu, the results are silently wrong, and you can't resume the rest of the model from outside.

Why dxinfer reads the file itself: dx-runtime's public API doesn't expose the task graph before a model is loaded. Its model parsers exist inside libdxrt.so but aren't exported, and the C parse call only prints to stdout. The graph is stored in the .dxnn file, as JSON that lists each task's device and how the tasks connect.

One-slide version of this section for presenting: auto-ort.html (online).

Decision logic

Every network goes through the same four stages when it loads. The model's shape is worked out first. Then your OrtMode choice is applied to it: Auto, the default, lets dxinfer decide from the shape, while On and Off are explicit. An explicit Off is respected, except on a model with two or more NPU tasks, where it would give wrong results, so loading stops. A task is one piece of the compiled model that runs on the NPU or the CPU, such as npu_0 or cpu_0.

After loading, if dx-runtime dropped ORT that dxinfer asked for, a MultiNpu model stops with LoadFailed, and a 1 NPU + CPU model gets a WARNING because its results are npu_0's raw tensors.

Evidence

  • The reader's output matches dx-runtime's own parse_model -v on two real models: YOLOV5S_Face (v9) and yolo26n (v8), both npu_0 → cpu_0.
  • 13 test cases cover every graph shape, every failure reason and every cell of the table.
  • On the NPU, yolo26-s-seg reported npu_0[NPU] -> cpu_0[CPU], and dx-runtime loaded 2 tasks, as the graph predicted.

Trade-offs

  • dxinfer duplicates knowledge of the .dxnn layout. The risk is contained: it's in one file, unknown versions fall back to ORT on with a WARNING, and a mismatch after loading is reported.
  • v6 files use an older graph layout and take the WARNING path.
  • Only the header and the graph JSON are read, a few KB, so the cost at load is negligible.

Recommended follow-up

  • Ask the dx_rt team for a public, structured task-graph query, such as a C function returning each task's name, processor and dependencies. dxinfer would use it when available and keep the reader as a fallback.

2. Multiple networks in one object

The problem

A real application usually runs several models: a detector plus a classifier, or several camera pipelines. Each needs its own engine, input and output buffers, completion handling and error handling. If the third model doesn't fit in NPU memory, the first two shouldn't be left loaded.

How dxinfer handles it

Behaviour

  • Loading: networks load in order. If any one fails, every network already loaded is released, which frees its NPU memory, and the error names them.
  • Out of memory: an NPU memory failure is reported as OutOfDeviceMemory, with each device's free memory in the message.
  • Queries by name: tensor layout, sizes, the task graph and stats are all looked up by network name.
  • Per-network options: device list, NPU core binding, buffer count and OrtMode.

Trade-offs

  • There's no ordering across networks. Each network's results are in order, and the app pairs them, e.g. with user_arg.
  • NPU memory is reserved at load and held until the object is destroyed. To swap models, you create a new object.
  • dxinfer is deliberately not a singleton. The application owns the object's lifetime, so shutdown happens while dx-runtime is still alive.

Evidence

  • Host tests: duplicate names are rejected before the device is touched, and each building block is tested.
  • The NPU run so far used one network. A multi-model run on the target is still to do, e.g. ./run.sh callback a.dxnn -n b=b.dxnn.

3. Automatic FIFO results

The problem

To keep the NPU busy, several jobs per network must be in flight at once: buffer_count × devices, 6 by default. They run on several NPU cores, plus ORT for the CPU tasks, so they finish in any order. Most applications, such as video, tracking or anything paired with input frames, need results in the order the inputs were fed.

How dxinfer handles it

Why the device stays full

  • A job's device slot is freed the moment it finishes, not when its result is delivered, so a waiting feed() refills the NPU at once.
  • In async mode dxinfer uses dx-runtime's completion callback, not a Wait in feed order, which would hold slots behind the slowest job.
  • A failed inference still produces a Result (with its error) in its place, so delivery never stalls.

Evidence from the NPU run

yolo26-s-seg · 1 network · 1000 jobs · async

  • 1000/1000 results in FIFO order, 0 failed
  • 109.5 FPS; peak in flight 6 / max 6 (device kept full)
  • Reorder wait: median 0.074 ms, p99 3.2 ms, max 40.5 ms

Source: the demo_callback -s -l 1000 output you shared.

Cost and how it shows

  • Results waiting their turn still hold their output block. When one early job is slow, for example at start-up warm-up, the spare blocks run out briefly.
  • That's what the warning in the NPU run showed. It now reports the breakdown (in flight / waiting for FIFO order / held by your app) and names the real cause.
  • Spare blocks are set with InferenceConfig::extra_result_buffers (default = in-flight count).

5. What users see at runtime

All messages go to stderr, one block per event, each prefixed with the network name. This is the current wording after the readability revision.

[dxinfer] autospeed: ONNX Runtime on (ort=auto). cpu_0 runs on the CPU after npu_0.
          Faster option: ort=OrtMode::Off, then implement cpu_0 yourself
          (results become npu_0's 10 raw tensors; listed by print_info()).
[dxinfer] WARNING autospeed: result blocks low (1 of 12 free)
          in flight 6 | waiting for FIFO order 5 | held by your app 0
          Cause: an earlier job is slow, so later results wait for their turn. Usually start-up warm-up.
          If it persists, raise InferenceConfig::extra_result_buffers (now 6).
[dxinfer] autospeed: result blocks recovered (3 of 12 free) after 6 ms
[dxinfer] det: WARNING: could not read the task graph of model.dxnn (unsupported .dxnn format v10
(reader supports v7-v9)). ORT: on (safe default). … please update dxinfer's model_graph reader.

The hint example uses the yolo26-s-seg network from the NPU run, which has 10 raw tensors. The breakdown numbers in the second block are illustrative: the NPU run used the earlier wording, and the new breakdown will be confirmed on the next run.
